Latent Verse / Part 3: finding structure

Clustering and labeling a map

Clustering algorithms find groups in the data and labels give those groups names. Both depend on choices we make.

By Ian Johnson

Grouping the dots with HDBSCAN

Looking at the UMAP scatter plot, your eye naturally groups the dots into clumps. Some areas are dense, others sparse. Clustering algorithms do this systematically: they assign every point to a group (or mark it as noise that doesn't belong to any group).

Here are the same 1,000 jokes, now colored by cluster. The algorithm we use is HDBSCAN, which finds clusters of varying density and size. Gray points are "noise": jokes that don't fit neatly into any group. One cluster is selected, and its jokes are listed under the map.

Loading the clusters…

Figure 1. HDBSCAN with min_cluster_size 5 finds 39 clusters. The legend lists the 20 largest, each named by three keywords from its jokes. Pick a cluster in the legend, or tap one of its dots, to read its jokes. The doctor cluster reads as a theme; the largest cluster, "dad, one, said", does not.

How many clusters should there be?

This isn't a question with one right answer. Clustering algorithms have parameters that control the granularity. With HDBSCAN, the key parameter is min_cluster_size: the minimum number of points required to form a cluster.

A small value finds many fine-grained groups. A larger value asks for bigger groups, and small ones either merge or dissolve into noise. Figure 2 starts at 10, twice the setting used above:

Loading the clusters…

Figure 2. The same jokes clustered at four values of min_cluster_size. The bar shows how the 1,000 jokes are divided: one segment per cluster, gray for noise. Colors are assigned per setting, so a color does not mean the same cluster from one setting to the next.

At 5, HDBSCAN finds 39 clusters and leaves 373 of the 1,000 jokes as noise. At 10 the result is very different: 802 jokes merge into one cluster with two small ones beside it. At 25 and 50 it goes the other way, and two or three clusters survive while about 70% of the jokes become noise. Neither view is more correct. On this map the fine setting is the one that finds specific themes, like the doctor jokes. The coarser settings mostly tell us that these 1,000 jokes form one cloud, without large groups that stand apart.

Naming the clusters

A cluster is just a set of indices until someone gives it a name. The legend in Figure 1 uses a simple kind of label, three keywords taken from each cluster's jokes. It works when a cluster has a subject with its own vocabulary, as in "doctor, dentist, tooth" or "into, bar, bartender". It says little for "dad, one, said", where the jokes share a storytelling format more than a topic.

Another approach is to sample a few items from each cluster and ask a language model to summarize what they have in common. The model reads 10-20 jokes from a cluster and proposes a label like "animal puns" or "jokes about family meals."

These labels are helpful but imperfect. A cluster might contain jokes that share a structural pattern (question-answer format) rather than a topic. The label the model generates depends on which samples it sees and how it interprets them. Different models produce different labels for the same cluster.

Which grouping is the right one?

Everything in this pipeline is interchangeable. You can swap the embedding model, the dimensionality reduction algorithm, the clustering method, the labeling approach. Each combination produces a different view of the same data.

A library can be sorted by author, subject, date, or reading level, and none of those is the true order. Clusters and their labels are the same kind of choice: ask which grouping is useful for the question you have, and try several, since each one is cheap to compute.

So far, every tool we've used has been local to this dataset. The UMAP projection reshuffles when the data changes. The clusters depend on the projection. In the next two articles, we'll build global tools: a set of features and a map that work the same way on any text, because they're trained to match the embedding model itself.
