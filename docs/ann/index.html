Approximate Nearest Neighbors

A series on finding neighbors in high-dimensional vector spaces: why exact search stops working, the three ideas that replace it, and how UMAP and semantic search put them to different uses.

query database vector nearest neighbors

Many machine learning applications depend on nearest-neighbor search over vectors. A semantic search turns a query into an embedding and asks an index which stored vectors are closest. A recommender asks the same about a user's vector. A dimensionality-reduction method like UMAP builds its whole output from a graph of nearest neighbors.

The direct method is to compare the query with every stored vector, and with millions of vectors of hundreds of dimensions that is too slow to do on every query. The tree structures that avoid it in two or three dimensions stop helping well before a hundred. So systems return approximate neighbors instead, and measure how many true neighbors they miss.

This series explains how those systems work, with figures that run the algorithms in the page on small datasets so you can see what they find and what they miss. It is organized around three ideas that production indexes combine: partition the space and search only the regions near the query; compress the vectors into short codes that are cheap to compare; and lay the index out for the hardware it lives on, whether RAM, SSD or GPU. We start in two dimensions, where everything can be drawn, and end with two applications that set the same three ideas in opposite ways.
