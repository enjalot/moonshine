Compress the Vectors

The second of three ideas behind approximate nearest-neighbor search: replace full-precision vectors with small codes that still let us estimate distance.

Part 3 of Approximate Nearest Neighbors

Partitioning cut down how many vectors a query is compared against. It left the vectors themselves alone, and they are large: an embedding model emits 768 or 1536 float32 values per vector, and every comparison has to read all of them from memory.

Compression shrinks each stored vector to a short code. That makes the database small enough to keep in memory, and it makes each comparison cheaper because there are fewer bytes to read. The price is that distances computed from codes are estimates, so this chapter keeps asking the same question of each scheme: how much smaller, and how wrong?

Why compress?

A 768-dimensional float32 vector is 768 × 4 = 3,072 bytes. A million of them take 3 GB and a hundred million take 307 GB, which is more RAM than most single machines have. The figure below does this arithmetic for several encodings at once.

Figure 1. Size of the whole database under each encoding, on a log scale, computed as vectors × bytes per vector. The vertical lines mark what a typical single machine offers: 64 GB of RAM and a 2 TB SSD (our assumption; move them in your head for your own hardware). At the default 100 million vectors, everything down to one byte per dimension is too big for RAM, and the product-quantized codes at the bottom fit with room to spare. Their size does not depend on the dimension at all.

We will look at three families. Scalar quantization stores fewer bits for each dimension. Binary quantization takes that down to one bit. Product quantization stops storing dimensions separately and spends its bits on groups of dimensions instead.

Scalar quantization: fewer bits per dimension

Pick a range for each dimension, divide it into equal steps, and store the index of the nearest step instead of a float. With 8 bits there are 256 steps per dimension and the vector is 4× smaller than float32. With 4 bits there are 16 steps and it is 8× smaller.

Every stored point moves to the nearest grid position, so points that were close stay close, with a rounding error of at most half a step per dimension. The comparison still touches every dimension, so the arithmetic is not reduced much; the gain is in the bytes read.

Figure 2. 200 points in two dimensions, each stored as its nearest grid position. The faint lines connect every point's true position to where its code puts it. Amber points are the query's true k nearest; purple rings are the k nearest computed from the stored positions. At 2 bits, 200 points share 16 grid positions, so many of them are tied and the rings land on the wrong ones. At 8 bits the grid has 65,536 positions and the two sets agree.

Binary quantization: one bit per dimension

At the limit each dimension keeps one bit: whether the value is above or below a threshold, usually zero or the dimension's mean. A 768-dimensional vector becomes 96 bytes. The distance between two such codes is the Hamming distance, the number of bits that differ, computed with an XOR and a population count. For 768 bits that is twelve 64-bit XOR-and-popcount operations in place of 768 multiply-adds.

Set Figure 2 to 1 bit to see how much this discards in two dimensions: every point collapses to one of four corners. With hundreds of dimensions there are far more bit patterns than points, and the pattern of signs often keeps enough of the neighborhood structure to produce a useful shortlist, which is then reordered with a more precise representation. How well that works depends on the embedding model.

Product quantization: one code per group of dimensions

Product quantization, or PQ, is the most widely used compression for vector search. It gets below one bit per dimension by giving up on dimensions as the unit. A byte encodes where a whole group of dimensions sits.

Split the d-dimensional vector into m subvectors of d/m dimensions each. For each of the m positions, run k-means over that slice of every database vector, usually with 256 centroids. Those centroids are the codebook for that position. Now each subvector can be replaced by the index of its nearest centroid, which is one byte, and the whole vector becomes m bytes.

Each position has only 256 choices, but the positions combine freely, so the codes can represent 256m distinct vectors. For m = 16 that is about 3 × 1038.

The figure below runs this on a small scale: 2,000 vectors with 8 dimensions, split into 4 subvectors of 2 dimensions so each codebook can be drawn. The codebooks are trained in the page with k-means.

Figure 3. Top row: one database vector. Middle: each pair of dimensions plotted in its own subspace, over a gray sample of the other vectors' values there. The purple dots are that subspace's trained centroids; the subvector is replaced by the nearest one, and the line between them is the error that introduces. Bottom: the code (one centroid index per subspace) and the vector it decodes to. With 4 centroids per codebook the decoded vector is visibly off; with 256 it is close, and the code is 4 bytes instead of 32.

The toy's 4 bytes for 8 dimensions is not below one bit per dimension, because its subvectors are tiny. Real settings use larger groups. With d = 768, FAISS indexes commonly use m between 16 and 64 with 8 bits each: 16 to 64 bytes per vector, which is 192× to 48× smaller than the 3,072-byte original, and between 0.17 and 0.67 bits per dimension.

Comparing a query to codes

We now have a database of codes, and a query that arrives as a full-precision vector. Decoding every database vector back to floats before comparing would give up the speed. PQ uses a lookup table instead, a scheme called asymmetric distance computation, or ADC.

Split the query into the same m subvectors. For each one, compute the squared distance to every centroid in that position's codebook. That is an m × 256 table, built once per query. The estimated squared distance to any database vector is then the sum of m table entries, one per byte of its code.

Figure 4. The lookup table for one query against the index from Figure 3 (4 subspaces, 16 centroids each). Each cell is the squared distance from one of the query's subvectors to one centroid; darker is closer. The rows below are five database vectors, chosen by their true rank for this query. Select one: its code picks one cell per row of the table (outlined), and the estimate is their sum. Compare the estimate with the true squared distance in the last column. The estimate is exactly the distance from the query to the decoded vector, so it is off by however far the decoding moved the vector.

The scheme is called asymmetric because only the database side is quantized; the query stays at full precision. The symmetric alternative quantizes the query too and reads centroid-to-centroid distances from a table computed once for the whole index. That saves building a table per query and adds the query's own quantization error, so asymmetric is the usual choice.

Reranking the shortlist

Because the estimates are off, the order of the nearest candidates gets shuffled, and some true neighbors drop out of the top k. The standard repair is to take more candidates than needed from the PQ ranking, a shortlist of R, then compute the exact distance for those R only and return the best k. This needs the original vectors to be kept somewhere, which can be slower storage since only R of them are read per query.

Figure 5. Same 2,000 vectors, searched with PQ codes. Left: the 25 best candidates for one query in PQ order. Bars are the PQ estimates, ticks are the true distances, and amber rows are the query's true 10 nearest; they are not all at the top, and the line shows where the shortlist ends. Right: recall@10 after reranking, against shortlist size, averaged over 100 queries, one curve per code size. Smaller codes need a longer shortlist to reach the same recall, which is the trade this chapter is about: bytes in memory against exact distances computed.

IVF-PQ: partition and compression together

The two ideas so far fit together. An IVF index decides which vectors a query looks at; PQ makes each look cheap. The combination, IVF-PQ, is the index FAISS is best known for and the one LanceDB builds by default.

A query picks its nprobe nearest cells, builds its lookup table, sums table entries for every code in those cells, keeps a shortlist, and reranks it with exact distances. The figure below runs that pipeline on 400 points and lets you stop after each stage.

One simplification in Figure 6: it encodes each point's coordinates directly. FAISS's IVF-PQ encodes the residual, the offset of the vector from its cell's centroid, which is smaller than the vector and so loses less to the same number of bits.

The same pattern shows up beyond IVF. Graph indexes can store PQ codes in place of full vectors at each node, and DiskANN keeps PQ codes in RAM to steer its search while the full vectors stay on SSD for the final rerank.
