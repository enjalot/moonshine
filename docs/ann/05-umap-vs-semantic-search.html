UMAP vs Semantic Search

Two uses of the same nearest-neighbor machinery. UMAP uses it once, over every point, to build a graph it then draws. Semantic search uses it on every query, for as long as the index is in service.

Part 5 of Approximate Nearest Neighbors

The previous four articles were about one operation: given a query vector and a large collection, find the vectors closest to it. This one is about two things people build on that operation, and how differently they use it. A UMAP projection needs the neighbors of every point at once, wants them as a graph, and never asks again. A semantic search service needs the neighbors of one unknown query at a time, quickly, indefinitely. The same three ideas (partition, compress, design for the hardware) get set differently for each.

UMAP: neighbors as the skeleton of a map

UMAP projects high-dimensional data to two dimensions so that a person can look at it. Its first step is to build a k-nearest-neighbor graph: every point is linked to its k closest points in the original space (k is the n_neighbors parameter, 15 by default). The distances along those links are converted to weights, scaled separately around each point so that dense and sparse regions are treated alike.

That graph is all UMAP knows about the data from then on. The second step is an optimizer that places the points in the plane, pulling linked points together and pushing randomly sampled pairs apart. The original vectors are not consulted again, so whatever the graph gets wrong, the map gets wrong.

The figure below runs a small UMAP in the page to see how wrong the graph can be. The data is 360 points in 10 dimensions lying along four curved strands. On the left, the layout from the exact graph. On the right, the layout from a graph whose neighbors were found using product-quantized codes, as in the compression article, with the code size under your control.

Hue marks the strand a point belongs to and lightness its position along the strand, so a faithful layout shows four smooth gradients. With 25-bit codes the graph has about nine tenths of the true neighbors and the two layouts match. With 10-bit codes it has about half: the strands are still separated from each other, and each one has broken into clumps. Points that share a code are tied in distance, so they link to each other and lose their order along the strand. Try k = 2 and k = 60 on the exact side as well: too few neighbors shatters the strands, more neighbors joins their pieces.

The UMAP in Figure 1 is a small reimplementation, simplified in three ways: it starts from the first two principal components where UMAP defaults to a spectral layout, it runs 150 epochs, and it uses fixed curve parameters (a = 1.577, b = 0.895, the values for min_dist = 0.1). The graph weights and the attract-and-repel updates follow the UMAP paper. Both sides use exact distances for the neighbors they found; only the choice of neighbors differs.

What does UMAP need from the index?

In Figure 1 the layout tolerates a graph that is missing a tenth of its true neighbors and degrades once about half are missing, and the damage shows up within clusters before it shows up between them. That is one toy dataset, and the thresholds will differ on real data, but the direction matches what large-scale practice reports: a graph built from heavily quantized vectors produces clumped maps, and builders of large maps measure graph recall against an exact sample and re-score candidates with exact distances before trusting the graph.

The other requirements follow from the shape of the job. Every point is a query, and all the queries are known in advance, so there is no need for an index that answers one arbitrary query fast. The reference UMAP implementation uses NN-descent, which builds the graph directly: it starts from a rough guess at each point's neighbors and repeatedly improves it by checking neighbors of neighbors. At larger scales the usual approach is the partitioning idea applied to construction: cluster the data, find neighbors within each cluster by brute force on a GPU, and assign points near a border to more than one cluster so that no neighborhood is cut by it.

Latency per query does not matter here; total build time does. For UMAP that build is most of the cost. One study of GPU UMAP (Park et al., "Massive-Scale Out-Of-Core UMAP on the GPU") found the k-NN graph taking up to 99% of the end-to-end runtime on GPU and over 75% on CPU.

Semantic search: neighbors as answers

Semantic search uses the same operation the other way around. A user types a sentence, an embedding model turns it into a vector, the index returns the closest document vectors, and those documents go back to the user or into a language model's context. The queries are not known in advance and they do not stop.

    Figure 2. A search over twenty sentences, with real embeddings: each sentence and each query was embedded with all-MiniLM-L6-v2 (384 dimensions) ahead of time, and the list ranks sentences by cosine distance to the query. The scatter is a projection of those embeddings onto their first two principal components, which carry 21% of the variance, so the five nearest are not always the five closest dots. Notice the fourth result for "bugs in a sorting algorithm": the search returns k results whether or not k relevant ones exist.

    What does semantic search need from the index?

    With twenty documents the search is a scan. With twenty million it is everything in the previous three articles, tuned for a latency budget: an answer within, say, tens of milliseconds, including on a bad day when other queries are competing for the same disk. The index can be expensive to build because that cost is paid once and shared by every query afterward.

    Compression is central here where it was a risk for UMAP, because a search has a cheap repair that a graph build does not. A query only needs its own top k to be right, so the index can rank with small codes held in RAM, keep a shortlist, and rerank that shortlist with exact distances. Recall is then tuned against latency, by raising nprobe, ef or the shortlist size until the budget is spent.

    The same three ideas, set differently

    UMAPSemantic search
    Partition Used during construction, to avoid comparing every point with every other. Points near a border are assigned to several cells so their neighborhoods stay whole. Used on every query. The number of cells or graph nodes visited is the main control for trading recall against latency.
    Compress Optional, and risky. Codes blur the order of near neighbors, which is what the graph is made of. When codes are needed to fit the data in memory, candidates are re-scored with exact distances. Central. Codes in RAM do the ranking, and a shortlist is reranked with full vectors. Without codes a billion-vector index does not fit in one machine's memory.
    Hardware Batch throughput. Every vector is a query, which is the workload a GPU rewards. The output is N × k edges: with k = 15, a 4-byte id and a 4-byte weight each, 120 bytes per point. Latency per query. Codes in RAM, full vectors on SSD, hot partitions in the page cache. A GPU helps only when queries arrive in batches.

    Where does the work go?

    We can compare the two workloads in the unit the series has used throughout, distance computations, for one concrete index: a million vectors in an IVF index with 1,000 cells, searched with nprobe = 10. Adding the vectors costs N × nlist comparisons to assign each one to a cell. A query costs nlist comparisons to rank the cells plus the vectors in ten of them.

    Figure 4. Distance computations for the two workloads on the same index, computed from the formulas above. Teal is building the index, orange is querying it. The UMAP bar never changes: its graph needs exactly N queries, one per point, and then the job is over. The search bar starts smaller, matches the graph build once the service has answered a million queries, and keeps growing. Left out: training the centroids, and UMAP's layout step, which is arithmetic on 2D coordinates and not distance computations in the original space.

    So a k-NN graph over N points costs about as much as serving N queries, and it has to be paid before the first picture appears. A search service pays the same amount gradually and then goes on paying. That difference in timing, more than any difference in algorithm, is why one of them is tuned for total throughput and the other for the latency of a single request.
