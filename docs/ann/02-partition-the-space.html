Partition the Space

The first of three ideas behind approximate nearest-neighbor search: cut the vector space into regions so a query only searches the regions likely to hold its neighbors.

Part 2 of Approximate Nearest Neighbors

Using the clusters that real data has

The previous article ended with a kd-tree that, by 16 to 20 dimensions, examined nearly every point to answer one query. That measurement used points sampled uniformly at random from a cube, which is the hard case.

Real embeddings do not look like that. A sentence embedding has 768 or 1536 dimensions, but the vectors a corpus produces clump by topic, by language, by style, by whatever the model learned to separate. The data behaves as if it had far fewer dimensions than the space it sits in.

Partitioning uses those clumps. We group nearby vectors into regions ahead of time, and at query time we find the few regions near the query and scan only those. There are three common ways to draw the regions: IVF puts them around learned centroids, LSH cuts them with random hyperplanes, and graph indexes such as HNSW replace explicit regions with links between neighboring points.

IVF: cluster the database, scan one cell

Run k-means on the database to get a set of centroids, and assign every vector to its closest one. Each centroid now owns a list of vectors, and the set of lists is called an inverted file, which is where the name IVF comes from. At query time we compare the query to the centroids, which is cheap because there are few of them, and scan the list of the nearest one. We will call the number of centroids nlist, as FAISS does.

Move the cursor over the plot, tap it, or focus it and use the arrow keys.

Figure 1. 220 points, clustered with k-means; the lines are the borders between cells. The search scans only the teal cell, the one whose centroid (square) is closest to the query, and returns the best point it finds there (solid line). The figure opens on a query where that is the wrong answer: the true nearest neighbor (dashed line) sits just across a border, in a cell that was never scanned.

The saving is easy to count. A query costs nlist centroid comparisons plus a scan of one list. If the cells are roughly equal, a list holds N / nlist vectors, so with nlist = 100 and N = 1 million a query makes 100 + 10,000 distance computations instead of a million.

The centroids are fit to the data, so cells are small where the data is dense and large where it is sparse. That is also the method's dependency: an IVF index has to be trained on a representative sample before anything is added to it, and if the data drifts away from that sample the cells stop matching it.

Probing more than one cell

Figure 1 shows the failure of single-cell search. A neighbor is missed whenever it was assigned to a different centroid than the query, which happens when the two sit on opposite sides of a cell border, however close together they are. The fix is to scan the nprobe closest cells instead of one.

As nprobe grows from 1 toward nlist, recall climbs toward exact and the work climbs toward a linear scan. The figure below shows both for one index: the left panel is a single query, the right panel is the average over many.

Drag nprobe. Move the query with the cursor, a tap, or the arrow keys.

Figure 2. An IVF index with 40 cells over 600 points. Left: the probed cells are teal; the query's true k nearest neighbors are amber, filled if a probed cell contains them and hollow if they were missed. Right: recall against the share of the database scanned, averaged over 200 queries placed near the data. The dashed diagonal is what scanning a random subset of that size would find. One probe finds about two thirds of the neighbors; three or four find nearly all of them. This toy is easy because a cell in two dimensions has only a handful of adjacent cells. In high dimensions a cell borders many more cells, which is why real indexes often probe tens of cells out of thousands.

The choice of nlist moves this curve. More cells mean shorter lists but more borders for a neighbor to fall behind, so a higher nprobe is needed for the same recall. The total work is about nlist + nprobe · N / nlist distance computations, which is smallest when nlist is near √(nprobe · N). That square root is why IVF guidelines scale nlist with √N.

LSH: partitioning with random hyperplanes

IVF has to be trained, and its cells only fit the dataset they were trained on. Locality-sensitive hashing, or LSH, partitions without looking at the data at all. In its random-hyperplane form, each hyperplane splits space into two halves and gives every vector one bit, depending on the side it falls on. With h hyperplanes each vector gets an h-bit code, and vectors with the same code share a bucket.

Two vectors separated by a small angle are unlikely to be split by a random hyperplane, so near neighbors tend to share a bucket. Each added hyperplane makes buckets smaller, which means less to scan, and gives every pair of neighbors one more chance to be separated.

Point at, tap, or arrow-key to a point to select it.

Figure 3. Random hyperplanes (lines, in two dimensions) through the center of 180 points. The selected point's bucket is purple. Its ten true nearest neighbors are ringed in amber: a ring around a purple point is a neighbor the bucket kept, a ring around a gray point is one that a hyperplane cut off. Add hyperplanes and the bucket shrinks, and so does the share of neighbors it keeps.

LSH needs no training, since the hyperplanes are drawn once at random and work for any dataset, and the probability that two vectors collide can be written down as a function of the angle between them. A single table loses too many neighbors, as the figure shows, so practical LSH builds several independent tables and scans the union of the query's buckets. More tables recover recall and add work.

Ignoring the data is also the weakness. Random hyperplanes spend bits on empty regions and leave dense ones undivided, so for the same amount of scanning, methods that look at the data usually reach higher recall. LSH is still used where the data changes too fast to retrain, and it is the easiest of the three to analyze.

Graph indexes: walking toward the query

The third approach stores a graph. Every vector is a node linked to some of its near neighbors, and a query is answered by walking: start at an entry node, look at its neighbors, move to whichever is closest to the query, and repeat until no neighbor is closer.

A walk over short links alone would cross a large dataset one small hop at a time. HNSW (Hierarchical Navigable Small World) adds layers. Every node is in the bottom layer, a random fraction are also in the layer above, and a fraction of those in the one above that. The upper layers have few nodes, so their links are long. A query starts at the top, walks until it stops improving, drops a layer at the node it reached, and continues.

Move the query with the cursor, a tap, or the arrow keys.

Figure 4. A three-layer graph over 140 points, built by HNSW's insertion procedure. The walk (amber) always enters at the same top-layer node (ringed), takes long hops there, then shorter ones in each layer below. The readout counts every distance the walk computed, and says whether it ended on the query's true nearest neighbor. Move the query around: it usually does, and sometimes stops one node short.

Two simplifications in Figure 4. The walk is purely greedy, keeping only its single best node; HNSW keeps a list of the best ef candidates in the bottom layer and expands all of them, which is how it avoids stopping one node short and how it trades work for recall. And with 140 points the layers are tiny; the hierarchy pays off when the bottom layer has millions of nodes.

The links are what the method depends on. HNSW does not connect each node to its nearest neighbors only: when it picks links for a node it skips a candidate that is closer to an already chosen neighbor than to the node itself, which spreads the links out in different directions. Figure 5 includes a graph built without that rule, and it shows why the rule is there.

Graph indexes cost more to build than IVF, because every insertion is itself a search, and they cost memory: on top of each vector, hnswlib stores about 8 · M bytes of links, where M is the number of links per node. HNSW is the default index in Weaviate and Qdrant, and pgvector offers it alongside IVF.

Comparing the three on one dataset

All three methods trade recall against work, each with its own knob: nprobe for IVF, the number of tables for LSH, the candidate list size ef for a graph. To compare them we built all three in this page over the same data and swept each knob. Work is counted in distance computations per query, as a share of the database, so a full scan is 100%.

Figure 5. Measured in this page: recall@10 against distance computations per query, for 2,000 points in 16 dimensions (20 Gaussian clusters) and 100 queries. Up and to the left is better. Each dot is one setting of the method's knob. IVF has 45 cells; LSH uses 8 hyperplanes per table; the graph is a single-layer HNSW-style graph with M = 8. The dashed line is a plain 8-nearest-neighbor graph searched the same way: with only nearest-neighbor links the clusters are barely connected to each other, and many walks that start in the wrong cluster never reach the right one, however long the candidate list.

This is a small experiment and it counts distance computations, not time, so it leaves out memory access patterns, SIMD and everything else the hardware article is about. At 2,000 points the three methods are within a small factor of each other. The gap widens with scale, because a graph search grows roughly with log N while an IVF scan grows with √N. On the million-vector datasets tracked by ann-benchmarks, graph indexes have held the best recall for a given query rate for years, with IVF variants behind them and LSH further back.

In practice the choice also depends on what else the index has to do. IVF builds quickly, has one main knob, and its lists are contiguous blocks that compress and page well, which matters in the next two articles. HNSW gives the best recall per query when everything fits in memory. LSH needs no training and tolerates data that changes constantly.

What partitioning leaves untouched

All three methods reduce how many vectors a query is compared against. None of them makes a single comparison cheaper. Each one still reads every dimension of a stored vector: for 1536-dimensional float32 vectors that is 6 KB of memory and 1,536 multiply-adds per comparison. With hundreds of millions of vectors, even a small share of the database is a lot of bytes to read.
