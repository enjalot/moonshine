Hardware-Aware Design

The third of three ideas behind approximate nearest-neighbor search: lay the index out for the device it lives on. RAM, SSD and GPU each reward a different layout.

Part 4 of Approximate Nearest Neighbors

Partitioning reduced how many vectors a query touches, and compression reduced how many bytes each one takes. Both articles counted work in distance computations. A real machine does not charge the same price for each one: the cost depends on where the bytes are when the query asks for them.

How long does one read take?

A computer stores data in a hierarchy. Reading a value already in the CPU's L1 cache takes about a nanosecond. The other cache levels are within a factor of ten or so of that. Main memory is about a hundred times slower than L1, a random read from an NVMe SSD is about a thousand times slower than main memory, and storage reached over a network is slower again.

Figure 1. Time for one random read at each level, on a log scale where every gridline is 10×. These are round order-of-magnitude figures in the tradition of the "latency numbers every programmer should know" list, not measurements of a particular machine. The right-hand column rescales them so that an L1 hit takes one second: on that clock a read from main memory takes under two minutes and a read from SSD takes more than a day.

Two consequences follow for an index. A scan that walks through memory in order is much cheaper per byte than these numbers suggest, because the CPU fetches ahead and the reads overlap; a search that jumps to an unpredictable address pays the full price each time. And the same jump that costs 100 nanoseconds in RAM costs 100 microseconds on an SSD, so a design built on pointer-chasing can be the fastest in memory and the slowest on disk.

In memory: everything fits

When the whole index fits in RAM, both styles work. A flat index (FAISS calls it IndexFlat) compares the query to every vector in order, using SIMD instructions that process 8 or 16 float32 values at a time. A graph index like HNSW hops between nodes, and each hop is a cache miss of around 100 nanoseconds, which is affordable for the few hundred hops a query makes.

How far a scan gets depends on bytes. Assume a core can stream on the order of 10 GB per second from memory. Ten million 768-dimensional float32 vectors are 30.7 GB, so one core needs about three seconds to scan them. The same ten million vectors as 64-byte PQ codes are 640 MB, which is around 60 milliseconds. This is the arithmetic behind keeping codes in RAM even when the full vectors would fit.

On disk: counting round trips

A billion 768-dimensional float32 vectors take 3 TB. Machines with that much RAM exist and are expensive; an SSD that size is ordinary. The question is how to answer a query while reading very little of it.

Suppose we put a graph index on the SSD unchanged. To decide where to hop next, a search needs the distance from the query to each neighbor of the current node, and so it needs each neighbor's vector. With 64 neighbors per node and 100 hops that is 6,400 random reads, and at 100 microseconds each, issued one after another, 640 milliseconds per query.

DiskANN is the best-known design for this setting, and it removes that cost in two steps. First, it keeps a PQ code for every vector in RAM, and uses those codes to compute the neighbor distances, so the search only reads from disk the nodes it actually expands. Each node's full vector and neighbor list are stored together in one disk block, so one read returns both. That brings 6,400 reads down to about 100. Second, it does not issue those reads one at a time. Each round, the search picks the W closest candidates it has not yet expanded and requests all W blocks at once. An NVMe drive serves a handful of concurrent reads in about the time of one, so latency follows the number of rounds, not the number of reads. W is called the beam width.

Raising W shortens the timeline and adds squares: fewer round trips, more reads in total, because some of the blocks fetched in a wide round turn out not to be needed. Past a certain width the round trips stop falling and only the reads keep growing.

Simplifications in Figure 2: the graph is built with the HNSW-style insertion from article 2, where DiskANN uses its own construction algorithm, Vamana; distances to unexpanded neighbors are exact, where DiskANN would use the PQ codes in RAM; the candidate list holds 10 nodes; and the latency estimate assumes the reads within a round overlap completely.

The full vectors that arrive with each block are also what the search uses for its final rerank, so the exact pass from the compression article costs no extra reads. The DiskANN paper (Subramanya et al., NeurIPS 2019) reports a billion-vector index served from one workstation with 64 GB of RAM and an SSD, at over 5,000 queries per second with mean latency under 3 milliseconds and better than 95% 1-recall@1.

On disk with IVF: a few long reads

An IVF-PQ index suits a disk for a different reason. Each cell's codes are stored as one contiguous run, so a query needs one read per probed cell, and each read is sequential, which is the access pattern drives are best at. LanceDB works this way: it keeps vectors in Lance, a columnar file format, builds an IVF-PQ index beside them, and reads the probed partitions when a query arrives. The operating system's page cache keeps recently read partitions in RAM, so partitions that are queried often stop costing disk reads at all.

Figure 3. An IVF-PQ index file drawn as one strip: 12 partitions of different sizes, each a contiguous run of 16-byte codes. The orange partitions are the ones this query probes, in order of centroid distance. The number of separate reads equals nprobe, and the bytes read are the sizes of those partitions; nothing else in the file is touched.

At a realistic size the same arithmetic gives the cost of a query. With 100 million vectors in 10,000 partitions, a partition holds about 10,000 vectors. With 64-byte codes plus an 8-byte id each, that is 720 KB per partition, and a query with nprobe = 20 reads about 14 MB in 20 sequential runs. Reranking with full vectors adds one random read per shortlisted vector unless they are cached.

On a GPU: throughput over latency

A GPU runs thousands of simple operations in parallel, which fits distance computation well: comparing a batch of queries against a block of vectors is one large matrix product. It also charges a fixed cost for every batch, to move the queries onto the device, launch the computation and copy the results back. A single query pays that whole cost alone, and a large batch spreads it across every query in it.

The figure below is a model of that trade with two numbers you can set. It is not a measurement, since both numbers depend on the hardware and the index, but the shape of the curve does not.

Figure 4. A cost model, in units of the time one CPU core takes to answer one query. The CPU answers one query per unit, whatever the batch size. A GPU batch of b queries takes (fixed cost) + b / (speedup) units, so its throughput is b divided by that. Below the crossover the fixed cost dominates and the CPU is faster. Far above it the GPU approaches its full speedup, and every query in the batch waits for the whole batch to finish.

This is why GPU indexes, including the ones in FAISS, are used mostly for work that arrives in bulk: embedding a corpus, searching with many queries at once, or building a nearest-neighbor graph, where every vector in the dataset is a query. The last case is the subject of the next article. For queries that arrive one at a time and need an answer in milliseconds, the fixed cost usually keeps the search on the CPU.

At 100 million vectors the layouts that keep full vectors in RAM are out, and the compressed ones use a few gigabytes. Step to a billion and the 64-byte codes alone pass 64 GB, which is the point where designs that keep a smaller code in RAM and everything else on disk take over.

Memory only rules layouts out. Choosing among the ones that remain depends on the latency target, the query rate and the recall needed, and the earlier sections give the direction of each: graphs in RAM give the lowest latency at high recall, IVF-PQ gives the smallest footprint and reads disks well, a disk graph serves the largest collections from one machine, and a GPU pays off when queries come in batches.
